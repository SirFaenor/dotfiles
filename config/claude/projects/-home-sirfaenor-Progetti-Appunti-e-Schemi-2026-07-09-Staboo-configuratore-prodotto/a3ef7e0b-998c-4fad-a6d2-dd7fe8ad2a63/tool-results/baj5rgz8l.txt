# 1. Contesto e Obiettivi del Progetto

L\'azienda intende dotarsi di uno strumento digitale riservato ai propri
commerciali (interni ed esterni) per semplificare e standardizzare il
processo di presentazione dei prodotti ai clienti finali. Lo strumento,
denominato Configuratore Prodotto, consente al commerciale di:

-   Ricercare prodotti applicando filtri sulle caratteristiche tecniche
    richieste dal cliente

-   Visualizzare i prodotti compatibili con relativo codice prodotto e
    dettagli tecnici

-   Generare dinamicamente la scheda tecnica del prodotto selezionato,
    in formato PDF

-   Scaricare o stampare la scheda per inviarla al cliente con i propri
    strumenti

-   Tracciare le attività svolte, in vista dell\'integrazione futura con
    il CRM aziendale

Il progetto si inserisce in un più ampio piano di digitalizzazione
commerciale che prevede, nelle fasi successive, l\'integrazione con ERP
e CRM. Il primo obiettivo è avere uno strumento funzionante e autonomo
per la ricerca prodotti e la generazione delle schede tecniche.

# 2. Utenti e Gestione degli Accessi

## 2.1 Tipologia di Utenti

Il portale è riservato esclusivamente al personale commerciale. Sono
previste due categorie di utenti:

-   **Commerciali interni:** dipendenti diretti dell\'azienda.

-   **Agenti / Commerciali esterni:** collaboratori o agenti di zona non
    dipendenti diretti.

  ----------------------- -----------------------------------------------
  **Utenti iniziali       \~3
  (go-live)**             

  **Utenti a regime**     \~30

  **Profili utente        Admin commerciale + Commerciale standard
  previsti**              
  ----------------------- -----------------------------------------------

## 2.2 Livelli di Accesso

Il sistema deve prevedere almeno due livelli di accesso distinti,
gestibili da un amministratore:

-   **Admin commerciale:** gestione degli account utenti (creazione,
    modifica, disattivazione), assegnazione dei mercati/prodotti
    visibili per ciascun commerciale.

-   **Commerciale standard:** accesso al configuratore e alle
    funzionalità di ricerca e generazione schede. Visibilità limitata ai
    prodotti del proprio mercato di riferimento.

+-----------------------------------------------------------------------+
| **Esempio di restrizione per mercato**                                |
|                                                                       |
| Un commerciale che opera sul mercato americano avrà accesso solo ai   |
| prodotti omologati/disponibili per quel mercato, che potrebbe essere  |
| un sottoinsieme del catalogo completo. Questa logica deve essere      |
| configurabile dall\'admin.                                            |
+-----------------------------------------------------------------------+

## 2.3 Sistema di Login

Sono allo studio due scenari di autenticazione, da valutare con il
consulente:

-   **Scenario A --- Login standalone:** username e password creati e
    gestiti internamente al portale, con funzione di reset password
    autonoma via email. Soluzione più rapida da implementare.

-   **Scenario B --- Login tramite Microsoft (SSO):** autenticazione
    federata con Microsoft Entra ID. Richiede che tutti i commerciali
    abbiano un account aziendale Microsoft. Offre maggiore sicurezza e
    un\'esperienza unificata.

+-----------------------------------------------------------------------+
| **Decisione richiesta**                                               |
|                                                                       |
| Prima dell\'avvio dello sviluppo occorre decidere quale scenario di   |
| login adottare. Bisognerà illustrare vantaggi, costi e prerequisiti   |
| di entrambi gli approcci.                                             |
|                                                                       |
| In caso di Scenario B, verificare che tutti i commerciali (inclusi    |
| gli esterni) abbiano o possano ottenere un account Microsoft          |
| aziendale.                                                            |

# 3. Catalogo Prodotti e Gestione dei Dati

## 3.1 Dove Vivono i Dati Oggi

I dati di prodotto sono attualmente conservati in un database locale
provvisorio. In una fase successiva migrerranno sull\'ERP aziendale. Il
portale dovrà pertanto essere progettato per supportare entrambe le
modalità:

-   **Fase 1:** connessione al database locale (soluzione transitoria
    per il go-live).

-   **Fase 2+:** integrazione diretta con l\'ERP, che diventerà la fonte
    dati primaria e autoritativa.

|                                                                       |
| Il catalogo attuale conta circa 4.000 prodotti ma il dimensionamento  |

| devono essere progettati per reggere questo volume fin dall\'inizio,  |
| senza richiedere una rearchitettura futura.                           |
+-----------------------------------------------------------------------+

## 3.3 Struttura dei Prodotti

I prodotti non sono liberamente configurabili: esistono combinazioni
predefinite e validate. Il sistema è un motore di ricerca/filtro su un
catalogo di prodotti finiti con codice univoco.

I parametri di ricerca principali, identificati con l\'ufficio
commerciale, sono:

-   Dimensione (lunghezza × larghezza)

-   Tipologia pannello (es. OSB, FSB)

-   Spessore

-   Densità

-   Core (parametro principale che definisce le caratteristiche di
    resistenza del pannello)

-   Emissioni

-   Resistenza meccanica

-   Finitura superficiale

-   Tipologia di bordo (es. Flat, T&G, Coda di rondine)

# 4. Funzionalità del Configuratore

## 4.1 Logica di Ricerca

Il commerciale accede al configuratore, imposta i parametri tecnici
richiesti dal cliente e il sistema restituisce i prodotti che soddisfano
tutti i criteri selezionati, con relativo codice prodotto.

Sono allo studio due approcci di interazione da valutare con il
consulente:

-   **Approccio A --- Filtri liberi:** tutti i parametri di ricerca sono
    visibili contemporaneamente. Il commerciale imposta i valori e il
    sistema aggiorna dinamicamente i risultati.

-   **Approccio B --- Wizard a step:** l\'interfaccia guida l\'utente
    passo per passo. Più adatto a utenti meno tecnici.

**Funzionalità \"Mixer\" (opzionale --- Da valutare)**

È in valutazione una funzionalità di ricerca avanzata di tipo \"mixer\":
il commerciale varia un parametro principale e i prodotti compatibili si
aggiornano in tempo reale. L\'adozione di questa funzionalità dipende
dalla complessità implementativa e dai costi aggiuntivi. Il consulente è
invitato a valutarne la fattibilità e l\'impatto sul progetto.

## 4.2 Risultati della Ricerca

I risultati devono mostrare almeno:

-   Codice prodotto univoco

-   Nome/descrizione del prodotto

-   Valori dei parametri principali usati nella ricerca

-   Indicazione visiva del \"core\" (con colore differenziato per
    tipologia)

-   Immagine rappresentativa del pannello grezzo (differenziata per
    tipologia, es. OSB vs FSB)

-   Possibilità di selezionare il prodotto per generare la scheda
    tecnica

## 4.3 Nessun Risultato Trovato --- Logica \"Vedi di più\"

Quando la ricerca non produce risultati esatti, il sistema non deve
restituire un semplice messaggio di errore. È richiesta la seguente
logica:

-   Il sistema individua i prodotti che non soddisfano solo 1 o 2 dei
    parametri selezionati

-   Questi prodotti vengono presentati tramite un pulsante \"Vedi di
    più\" o equivalente, distinti visivamente dai risultati esatti

-   I prodotti suggeriti non hanno alcuna gerarchia tra loro: un
    prodotto che non corrisponde per \"core\" non è considerato più o
    meno rilevante di uno che non corrisponde per \"densità\". Tutti i
    parametri hanno uguale peso nella logica di suggerimento

+-----------------------------------------------------------------------+
| **Esempio operativo**                                                 |
|                                                                       |
| Ricerca con 5 parametri → nessun risultato esatto.                    |
|                                                                       |
| Il sistema trova: Prodotto A (non corrisponde per \"core\") e         |
| Prodotto B (non corrisponde per \"densità\").                         |
|                                                                       |
| Entrambi vengono mostrati nella sezione \"Vedi di più\" senza che uno |
| sia visualizzato prima dell\'altro o marcato come più rilevante.      |
+-----------------------------------------------------------------------+

# 5. Scheda Tecnica: Generazione e Formato

## 5.1 Generazione Dinamica

La scheda tecnica non esiste come PDF pre-caricato: viene generata
dinamicamente dal sistema al momento della richiesta, sulla base dei
dati strutturati del prodotto selezionato. Questo garantisce che la
scheda sia sempre aggiornata e coerente con il catalogo.

## 5.2 Template e Design

Tutte le schede tecniche condividono lo stesso template. Le variazioni
previste sono:

-   Colore identificativo del \"core\" del pannello (varia per tipologia
    di core)

-   Immagine del pannello grezzo (differente tra OSB e FSB)

-   Dati tecnici specifici del prodotto selezionato

Il template deve essere realizzato con il brand aziendale (logo, colori,
font). Il grafico interno dovrà essere coinvolto per la validazione del
design. Il formato della scheda allegata (EGGER DecoWall) è il
riferimento strutturale.

+-----------------------------------------------------------------------+
| **Elementi attesi nella scheda tecnica**                              |
|                                                                       |
| Intestazione con logo aziendale e dati documento (codice prodotto,    |
| numero revisione, data di generazione)                                |
|                                                                       |
| Identificazione prodotto: nome, codice, tipologia                     |
|                                                                       |
| Tabella caratteristiche tecniche e meccaniche (con norme di           |

|                                                                       |
| Tabella tolleranze                                                    |

|                                                                       |
| Certificazioni e marchi di qualità                                    |
|                                                                       |
| Note legali / disclaimer standard                                     |
+-----------------------------------------------------------------------+

## 5.3 Versioning della Scheda

La scheda tecnica deve includere un sistema di versioning. Ogni scheda
dovrà riportare:

-   Numero di revisione del prodotto (es. Rev. 03)

-   Data di generazione del documento (data in cui viene creato il PDF)

+-----------------------------------------------------------------------+
| **Decisione richiesta --- Logica di versioning**                      |
|                                                                       |
| Occorre definire se il numero di revisione è gestito manualmente      |
| dall\'admin (incrementato a ogni modifica del prodotto nel catalogo)  |
| o calcolato automaticamente dal sistema al rilevamento di modifiche   |
| ai dati.                                                              |
|                                                                       |
| Il consulente è invitato a proporre la soluzione più appropriata.     |
+-----------------------------------------------------------------------+

**6. Distribuzione della Scheda al Cliente**

## 6.1 Modalità di Distribuzione

La distribuzione della scheda tecnica avviene esclusivamente tramite gli
strumenti del commerciale, non attraverso il portale. Le funzionalità
previste nel portale sono:

-   **Download PDF:** il commerciale scarica il file sul proprio
    dispositivo e lo invia al cliente con i propri strumenti (email,
    WhatsApp, ecc.).

-   **Stampa:** stampa diretta della scheda dal browser.

+-----------------------------------------------------------------------+
| **Funzionalità escluse --- Invio email dal portale**                  |
|                                                                       |
| L\'invio di email direttamente dal portale non è richiesto. Il        |
| commerciale utilizzerà i propri strumenti per la comunicazione con il |
| cliente. Questa scelta semplifica l\'architettura, elimina la         |
| necessità di un server email dedicato e riduce le implicazioni GDPR   |
| legate alla gestione dei dati del destinatario.                       |
+-----------------------------------------------------------------------+

## 6.2 Tracciamento delle Attività

Il sistema deve registrare le attività svolte dai commerciali per
finalità di monitoraggio e futura integrazione con il CRM. I dati da
tracciare includono:

-   Utente che ha eseguito l\'azione

-   Prodotto selezionato (con codice)

-   Azione svolta (generazione PDF, download, stampa)

-   Data e ora dell\'azione

Questo log di attività dovrà essere accessibile all\'admin e, in fase 2,
sincronizzato con il CRM come traccia delle azioni commerciali.

## 7.2 Gestione dei Dati e GDPR

L\'invio email non è previsto nel portale, pertanto la gestione dei dati
del cliente destinatario non è in scope per questo strumento. I dati
personali dei clienti rimangono gestiti interamente dal CRM/ERP come
fonte autoritativa.

Il consulente dovrà comunque prevedere nella progettazione il rispetto
del GDPR (Reg. UE 2016/679) per quanto riguarda: trattamento dei dati
degli utenti del portale, misure di sicurezza sui dati in transito e a
riposo, localizzazione dei server (preferibilmente in UE).

# 8. Requisiti Multilingua

Il portale e le schede tecniche devono supportare più lingue. Il
requisito multilingua si applica a due livelli:

**Interfaccia del portale**

Il commerciale può scegliere la lingua dell\'interfaccia
indipendentemente dalla lingua dell\'output. Le lingue minime da
supportare (da definire con l\'ufficio commerciale) sono almeno italiano
e inglese, con possibilità di estensione futura.

**Scheda tecnica generata (output PDF)**

Il commerciale può scegliere la lingua del PDF indipendentemente dalla
lingua dell\'interfaccia. Esempio: un commerciale con interfaccia in
italiano può generare una scheda in inglese per un cliente straniero.

+-----------------------------------------------------------------------+
| **Implicazioni tecniche**                                             |
|                                                                       |
| Il supporto multilingua richiede che tutti i testi (interfaccia e     |
| scheda tecnica) siano gestiti tramite un sistema di localizzazione    |
| (es. file i18n). I contenuti tecnici (nomi parametri, unità di        |
| misura, note legali) devono essere tradotti e validati dall\'ufficio  |
| tecnico per ogni lingua supportata.                                   |
|                                                                       |
| L\'aggiunta di nuove lingue in futuro deve essere possibile senza     |
| modifiche strutturali al codice.                                      |
+-----------------------------------------------------------------------+

# 12. Domande per il Consulente

Il presente documento è il punto di partenza per il dialogo con il
consulente tecnico. Si richiede al consulente di:

-   Proporre l\'architettura tecnica più adatta (portale integrato nel
    sito vs. applicazione separata), tenendo conto della scalabilità
    fino a 100.000 prodotti

-   Valutare e confrontare i due scenari di autenticazione (standalone
    vs SSO Microsoft) con indicazione di costi e pro/contro

-   Proporre l\'approccio UX del configuratore (filtri liberi, wizard, o
    ibrido) con eventuale mockup

-   Valutare la fattibilità e il costo aggiuntivo della funzionalità
    \"Mixer\" parametri

-   Definire come strutturare la connessione al database locale in Fase
    1 e la migrazione verso l\'ERP in Fase 2

-   Proporre un piano per la generazione dinamica del PDF della scheda
    tecnica con gestione versioning

-   Definire l\'architettura multilingua più efficiente e scalabile
    (interfaccia + output PDF separati)

-   Illustrare come verranno gestiti il tracciamento attività e la
    futura integrazione con Salesforce

-   Proporre un piano di progetto con fasi, milestone e stime di tempo e
    costo

-   Segnalare eventuali requisiti mancanti o ambiguità che richiedono
    chiarimento
